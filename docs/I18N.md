# Übersetzungen (i18n) im Betreiber-Dashboard

Stand: 09.10.2026. Gilt für das Betreiber-Dashboard (`src/pages`, `src/components`).
Das Staff-Dashboard (`src/staff`, Routen `/staff/*`) bleibt bewusst deutsch.

## Wie es funktioniert

- Alle Texte stehen in `src/lib/i18n.tsx` im Objekt `translations`, je Sprache ein Block:
  `de`, `en`, `es`, `fr`, `it`, `nl`, `lv`. Alle Blöcke haben dieselben Schlüssel.
- In Komponenten: `const { t } = useI18n();` und dann `t('bereich.schluessel')`.
  Platzhalter: `t('pay.purchases_count', { count: 3 })` mit `{count}` im Text.
- Zahlen, Datum, Währung: `const locale = useLocaleTag();` (z. B. `de-DE`, `en-GB`) statt fest `'de-DE'`.
- Außerhalb von Komponenten (Hilfsfunktionen auf Modulebene): `translate(key, params)` und
  `currentLocaleTag()` aus `src/lib/i18n.tsx`. Die anzeigende Komponente ruft trotzdem
  `useI18n()` auf, damit sie beim Sprachwechsel neu rendert. Beispiel: `src/components/AutomatHealth.tsx`.
- Warnungen „… ist vorübergehend nicht erreichbar“ kommen aus `getOptionalSourceWarning`
  (`src/lib/edgeFunctions.ts`) und sind dort selbst übersetzt.
- Produkttexte der Upgrades (Tabelle `park_equipment_items`) stehen deutsch in der Datenbank.
  Die Anzeige wird im Frontend übersetzt (`src/lib/equipmentI18n.ts`, `src/lib/equipmentDescriptions.ts`).
  Die Preislogik liest immer den deutschen Originaltext.

## Neue Texte hinzufügen

1. Schlüssel nach Bereich benennen (`shop.*`, `crm.*`, `health.*`, `camera.*`, `builder.*` …).
2. Mit dem Helfer eintragen und ersetzen:

   ```python
   import sys; sys.path.insert(0, 'scripts')
   from i18n_apply import apply
   apply(
       {'shop.neuer_text': ['Deutsch', 'English', 'Español', 'Français', 'Italiano', 'Nederlands', 'Latviešu']},
       [('src/pages/Shop.tsx', '>Fester Text<', ">{t('shop.neuer_text')}<")],
   )
   ```

   Vorhandene Schlüssel werden nicht überschrieben. Vorher mit `grep` prüfen, ob es den
   Schlüssel schon gibt (Beispiel aus der Praxis: `health.title` war schon „Systemzustand“).
3. Prüfen: `npm run check:i18n` (alle Sprachen gleich, keine leeren Werte, Platzhalter passen,
   jeder `t('…')`-Schlüssel existiert), `npm run typecheck`, `npm run build`.

## Regeln für Texte

- Deutsch ist Johns Originaltext: beim Übersetzen **nie umformulieren** (auch nicht „Hosting“ → „Bereitstellung“,
  „Upgrade“ → „Erweiterung“, „&“ → „und“). Nur die anderen Sprachen werden geschrieben.
- Deutsch: Du-Form, „du/dein/dir“ mitten im Satz klein. Echte Umlaute (ä/ö/ü/ß), nie ae/oe/ue.
- Begriffe einheitlich: Online-Shop, Speedmessung, Konfiguration, Automat, Freischaltung, Upgrade.
- Übersetzungen natürlich, nicht wörtlich. Produktnamen (PrintBox, Cashbox, Stripe) bleiben.
- Buttons kurz halten, damit sie nicht umbrechen.

## Stand

- Übersetzt (alle 7 Sprachen, 1.465 Schlüssel je Sprache): Navigation, Übersicht, Umsatz
  (inkl. Zahlungsübersicht, Automaten-Verteilung), Käufe, Fotos, CRM (Übersicht, Kontakte, Umfrage,
  Social Media, Pixel, Kontakt-Einstellungen, Preise und Pakete), Online-Shop (inkl. Preisseite),
  Speedmessung, Personalisierung (inkl. „Overlays ändern“ und Overlay-Editor), Mitarbeiter,
  Systemzustand (inkl. Anlagenstatus), Kamera, Konfiguration (inkl. Produktseiten, Bestellungen),
  Einstellungen, Einführungs-Rundgang, Layout/Fehlerseiten.
- Bewusst nicht übersetzt:
  - Datenschutzerklärung und Support-Rechtsseite (`PrivacyPolicy.tsx`, `LegalSupport.tsx`) – Rechtstexte,
    sollten Fachleute übersetzen.
  - Öffentlicher Demo-Shop für Gäste (`DemoShop.tsx`) – eigenes Thema.
  - `Operations.tsx`, `Errors.tsx` – im Dashboard nicht verlinkt.
  - Texte, die der Server oder der Automat liefert (Hinweise im Systemzustand, Gerätenamen aus
    `geraeteNamen.ts`, Datenbank-Einträge wie die Geräteliste) – kommen deutsch an.
